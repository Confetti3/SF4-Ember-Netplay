# ember-reports

Opt-in crash and problem reports for SF4 Ember Netplay. The launcher posts to
`https://embernetplay.link/report/v1`; nginx streams the upload to
`127.0.0.1:47850`. The launcher consent UI, collection and redaction are a
separate task. This service assumes the player has opted in there.

## Build and test

Build in WSL Ubuntu 26.04 with Rust 1.98 or newer:

```sh
cd server/ember-reports
cargo test
cargo clippy --all-targets -- -D warnings
cargo build --release
```

This is an independent crate, like `ember-rooms` and `ember-short`. Include
the generated `Cargo.lock` with the first verified WSL build, then use `--locked`.
During the initial Windows edit-only task, `cargo test --offline` and
`cargo clippy --offline --all-targets -- -D warnings` both stopped at dependency
resolution: `breakpad-symbols` was missing from the local cache. No build/test
pass or runtime acceptance is claimed from those attempts.

The rust-minidump family (`minidump`, `minidump-processor`, `minidump-unwind`,
`breakpad-symbols` and test-only `minidump-synth`) is pinned to **0.27.0** with
default features, including the processor's `disasm_amd64` feature. WSL builds
with 0.26.1 and defaults disabled failed inside `minidump-processor`; 0.27.0 with
defaults compiled the dependencies, then exposed an event JSON macro error in
this crate. The source fix and API review have not yet been built or tested.
axum is pinned to **0.8.9**, enabling only HTTP/1, Tokio, JSON and multipart.
reqwest is pinned to **0.13.5**, without default features: Bugsink uses HTTP on
IPv4 loopback, without TLS, proxies or redirects. Symbol providers have no HTTP
feature. Other dependency ranges are in `Cargo.toml`; a WSL-generated lockfile
will record their resolved versions.

API references: [rust-minidump v0.27.0](https://github.com/rust-minidump/rust-minidump/tree/v0.27.0),
[Breakpad local symbol lookup](https://github.com/rust-minidump/rust-minidump/blob/v0.27.0/breakpad-symbols/src/lib.rs).

Tests cover multipart/metadata rejections, size boundaries and unknown-length
bodies, trusted-proxy addressing, sliding rates/Retry-After, queue saturation,
synthetic x86 dumps with/without local symbols, failed-walk raw facts, Sentry
shape/frame ordering/event size, fake Bugsink retries, outbox capacity, and dump
retention/permissions. Regressions also cover an adversarial shared x86
frame-pointer chain outside modules, child limits/kill/reap, padded module
lists and referenced ranges, reserved storage/failed writes, retained dumps on
full-outbox rejection, and fair delivery past a full batch of permanent or
unreadable failures. Synthetic dumps are generated by `minidump-synth` in tests.

## Schema 1 request

POST `multipart/form-data`, at most **5 MiB including boundaries**. One required
`meta` part, without a filename, contains JSON:

```json
{
  "schema": 1,
  "kind": "crash",
  "app_version": "0.8.0",
  "channel": "beta",
  "build_id": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "source_revision": "0123456789abcdef",
  "windows_version": "Windows 11 24H2",
  "exit_code": -1073741819,
  "exception_code": "0xc0000005",
  "crash_address": "0x401234",
  "comment": "The game stopped after joining a room."
}
```

`kind` is `crash` or `problem`; channel is `stable`, `beta` or `nightly`.
Build ID is 64 hex digits. App version/source revision are nonempty strings up
to 128 UTF-8 bytes; Windows version is up to 256 bytes, without control characters.
Meta is up to 16 KiB. Comment is optional, up to 2000 Unicode characters, not
bytes. Exit code is an optional Windows signed/unsigned 32-bit JSON integer.
Exception code/address are optional hex strings, with or without `0x`, up to
8/16 hex digits. Null optional values are allowed. Unknown JSON fields, wrong
types, missing required fields, duplicate parts and unknown parts are rejected.

Zero to four `log` parts are allowed. Each has a filename exactly equal to
`sf4e.log`, `launcher.log`, `sf4e-crash.log` or `sf4-net.log`, is UTF-8 text,
and is at most 192 KiB. Duplicate filenames and path components are rejected.
The launcher redacts logs before upload. The optional single `minidump` part is
at most 4 MiB and starts with `MDMP`; its filename is ignored. A damaged dump
with a valid signature still produces an event with raw facts and walk status.

After deciding to submit a redacted report:

```sh
curl --fail-with-body https://embernetplay.link/report/v1 \
  -F 'meta=<meta.json;type=application/json' \
  -F 'log=@sf4e.log;type=text/plain' \
  -F 'minidump=@crash.dmp;type=application/octet-stream'
```

Success is **202**, `{"id":"<32 lowercase UUID hex digits>"}`: the event is
durable in the local outbox, though delivery may be pending. Invalid input is
400, excessive bytes 413, slow upload 408, rate limit 429 with `Retry-After`,
and full/expired queue or unavailable storage 503. Responses are `no-store`.
GET returns 405 and can check the local listener without sending a report.

## Work and resource bounds

Sliding windows allow five attempts/address/ten minutes and 300 total/hour.
Bad input consumes a token too. Only a peer exactly equal to `127.0.0.1` may
supply one parseable `X-Real-IP`; otherwise the transport address is used.
nginx overwrites that header. The in-memory address table has 4096 entries and
refuses new addresses while full. No address is persisted or logged.

Four requests upload/process at once; 32 wait without reading their bodies;
the 37th gets 503. Queue waiting expires after 60 s and upload after 20 s.
The complete body, including multipart epilogue, is bounded and read before
validation; axum and an HTTP body layer also enforce the cap. After upload,
bounded processing/storage completes even if the client disconnects. Worker
permits stay held until work exits, including worker termination and reaping.

Parsing and walking run in a short-lived child of the same binary, invoked as
`ember-reports symbolicate <symbols-directory>`. The dump arrives on stdin and
JSON frames leave on stdout. Before exec the Linux parent installs hard/soft
`RLIMIT_AS` of **64 MiB**, `RLIMIT_CPU` of the configured processing seconds
(rounded up, at least one second), and zero core-file size. Four children have
at most 256 MiB of address space combined, leaving headroom within the service's
512 MiB cgroup. The parent enforces the wall deadline across pipe I/O, walking
and process exit, kills on timeout/error, and waits for reaping before releasing
admission. Worker stdout is capped at 8 MiB. An exhausted or crashed child
leaves intake and outbox delivery running and emits fixed raw exception facts
when available. Other platforms fail closed without in-process parsing.

The processor view includes only Windows thread/module/memory/exception/system
streams, excluding arbitrary extension streams and annotations. Input budgets
are 64 directory entries, 128 threads, 256 modules and 1024 memory ranges. List
streams must use the exact unpadded layout; module names and CodeView records
are capped at 1024 bytes with their referenced ranges checked before parsing.
Symbol files must be canonical paths within the symbol store, at most 8 MiB
each and 16 MiB total per walk. Missing, oversized or corrupt symbols leave
frames as module+offset. The child has a single current-thread runtime, with
no cooperative provider checkpoints or nested per-request runtime.

Sentry frames are innermost-last, retaining the nearest 64 per thread. Exported
frame fields are function, source basename/line, module, instruction address and
in-app status. Launcher.exe, Sidecar.dll, Updater.exe and sf4-net.exe are in-app.
Unsymbolicated crashing stacks use a fingerprint of
`["{{ default }}", "<top module>+0x<offset>"]`; unknown modules use the absolute
instruction address. Events carry channel/build/kind/Windows/exception tags,
release, comment, source revision, raw codes, report ID and saved dump path.
Problems use the comment as their message. Events stay strictly below 900 KiB
after JSON escaping: the crashing stack takes priority, auxiliary threads may
be limited, and logs retain UTF-8 tails when trimmed from their start.

## Storage and privacy

- `<state>/dumps/<id>.dmp`, 0600: raw dump for up to 30 days. Pruned on startup,
  each new dump and every minute; oldest first at 2 GiB or 4096 files. A dump
  can expire sooner, so a path recorded in Bugsink may later be absent.
- `<state>/outbox/<id>.json`, 0600: pending event JSON, at most 512 files/256 MiB.
  Full capacity rejects new reports; accepted pending events are not evicted.
  A storage reservation holds the capacity lock through commit, so concurrent
  requests cannot overbook. Both dump and event writes are staged and synced
  before publishing; failed writes clean up their new files before retention.
  Older dumps are pruned only after the new report is durable. Events are deleted
  only after Bugsink returns success. Writes sync file and directory before 202;
  killed writes' temporary files are removed on restart.
- `<state>/symbols/`: trusted owner-uploaded Breakpad symbols, not player data.
  Only this directory is group-writable; dumps/outbox are private 0700 directories.

No other player files or standalone logs/metadata are stored. Minidumps can
contain private process memory, paths and identifiers; log redaction does not
sanitize the dump. The launcher must explain this for the optional dump. Restrict
Bugsink/state access and configure Bugsink's event retention separately. The
30-day policy covers raw dumps, not Bugsink events or pending outbox JSON;
outbox events remain until delivery or explicit owner removal, within the caps.

The sole request journal line contains method, status, bytes read, report ID
(or `-` for rejection), processing milliseconds. There are no addresses,
contents or secrets in those lines. Parser panic messages are suppressed by a
static panic hook. No library logging subscriber is installed.
nginx disables report access logs and disk upload buffering. Secrets are loaded
only through systemd's credential directory, never event/config JSON.
