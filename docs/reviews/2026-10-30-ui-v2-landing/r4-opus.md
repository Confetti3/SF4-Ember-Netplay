## Findings, in priority order

### 1. The room-settings rule now opens edits the runtime refuses: watching a match ends in a stuck "Save failed"

ShellView::CanEditRoomSettings (src/ui/ApplicationShell.hxx) dropped `atMainMenu` and now reads `canEditPreferences || (session.room != Idle && !Fighting(session.match))`. Its comment and the commit message justify this with "the runtime takes them at once (SaveRoomSettings)". That is not what the runtime does. src/sf4e/sf4e__NetplayRuntime__Input.cxx:SaveRoomSettings begins `if (!CanEditButtonLayoutNow()) return;`, and CanEditButtonLayoutNow requires `AtMainMenu()`, which is true only while the game's "MainMenu" event is in the foreground (sf4e__NetplayRuntime.cxx:AtMainMenu). Both callers, Handle(commands::RoomSettings&) and the `command.roomSettings` branch of Handle(commands::Room&) in sf4e__NetplayRuntime__Room.cxx, go through that gate, and neither sf4e__NetplayRuntime__Input.cxx nor sf4e__NetplayRuntime__Room.cxx changed in this branch. While the game plays a watched match it is not at its main menu, and the same holds in Training and anywhere else off the menu while in a room. The finding does not rest on that reading of the event system alone: the author's own journey models watching as `atMainMenu = false`, and the runtime drops every roomSettings command in that state.

Trace in the game, in exactly the state the commit set out to open (in a room, watching, `match == None`, not at the main menu): the player drags the watched picture or a grip, or steps a Room layout row. `preferencesDirty_` is set, UpdatePreferenceSave finds MaySave true, SavePreferences sends a `roomSettings` request, and the runtime drops it without an error. `v.preferences` never reaches `savingPreferences_`, so two seconds later UpdatePreferenceSave sets `saveFailed_` with `error.settings_not_saved`. The footer's Retry saving is then open (it is enabled by the same MaySave), and every retry is dropped and fails the same way until the player returns to the menu. Background does the same while Ember is hidden. Before this commit the shell held these edits until the main menu, which the runtime accepts; round 3 turned a deferred save into a failing one.

The test cannot see it. RoomSettingsFollowOneRule models "the fight over, the game still running the watched match" as `atMainMenu = false; match = None` and asserts `RoomSaves(h, second) == 1`, which counts the shell's sends; the harness accepts every action and the test then hands the sent preferences back as the snapshot, so the runtime's refusal is never exercised. So the branch now has two rules for the same settings again (Sol 1 / room-audit 16 in the opposite direction): the shell's and the runtime's.

Remedy: make the two gates one rule. The direct move is in the runtime: give SaveRoomSettings its own predicate that mirrors ShellView::CanEditRoomSettings (`!Fighting(match) && (canEditPreferences || room != Idle)`), and keep CanEditButtonLayoutNow, with its AtMainMenu, only on the Layout and RemoveLayout pad requests. SaveRoomSettings should keep copying the whole room-settings set: the shell already keeps button layouts menu-only (CanEditLayout requires `atMainMenu`), and a partial copy would make the saved snapshot differ from what the shell sent, which UpdatePreferenceSave (SamePreferences against `savingPreferences_`) would again time out as Save failed. The fix is the gate alone. Confirm that OverlayPrefs::SavePlayerPreferences is safe to call while a match runs, since it has only ever been reached at the main menu. Pin it with a runtime test in the pattern of spectator_runtime_test.cxx (SetAtMainMenuForTest(false), a joined room, `match == None`, a roomSettings command, the saved board layout and picture), and fix the ShellView comment and commit message to match. If the runtime should not save off the menu, the alternative is to restore `atMainMenu &&` in CanEditRoomSettings and drop the "watching included" wording; DrawWatchedPicture's `movable` would then always be false, so the picture's drag and resize should be deleted rather than gated. Either way, the shell and the runtime must read the same rule, and a test must run the runtime's side.

### Notes (not blocking)

A. ShowTab's name and header comment describe a Settings tab or panel opener, but it is now the Shortcut handler for every tab strip (replays, rankings, awards, news). The behaviour matches the old code; say so in the header comment, or name it for the tab strip. Home's `settings` row still uses `nav.Push("tab-player")` (ApplicationShell.cxx:HandleActivate); equal at the root, but it is the one exception to "ShowTab is the one way".

B. MenuNavigation::Update now uses geometry only when `placed_.size() > 1`. The threshold stands for "only the footer was placed", but it also switches any body that places exactly one row of its own to order navigation. I found no such body today, so this is a legibility item in a shared path: state the condition it means (a placed row with no placed neighbour falls back to row order), or have DrawBody not place the footer when the body placed nothing.

C. The test for "a choice is drawn as a popup" is now written twice: GameMenu::Finish (`!f.body && !f.valuePanel` before DrawChoiceModal) and DrawHintBar's `popup`. A small `ChoiceIsPopup(f)` used by both keeps the hints and the modal from drifting apart.

## What unblocks approval

Finding 1 alone. Everything round 3 asked for is in the code and checks out, including both file splits, the footer, ShowTab and the pointer gates. But the commit's central premise about the runtime is false at HEAD, the broadened rule turns a deferred save into a repeating save failure in the watched-match case it was written for, and the new journey measures the send rather than the save. Align the runtime and the shell on one rule, with a runtime test, and I would approve.
