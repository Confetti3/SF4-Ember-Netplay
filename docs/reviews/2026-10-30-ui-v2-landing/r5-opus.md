### Note 1 (not blocking). SaveRoomSettings keeps a conditional SetLayouts that the layer does not need

sf4e__NetplayRuntime__Input.cxx:SaveRoomSettings ends with `if (CanEditButtonLayoutNow()) Gamepads::SetLayouts(...)`, defended by a comment that off the menu "these are the layouts in use". That holds today, because the shell's ChangeLayout requires CanEditLayout (at the main menu) and so the shell cannot send changed layouts off the menu. But the runtime does not enforce it, and TestWatcherSavesRoomSettings actually pins the opposite case: a roomSettings command off the menu with a new layout is taken into runtime->preferences and written to disk while Gamepads keeps the old set until the next main-menu save or restart. The guard also buys nothing: GamepadLayouts::Set is a plain assignment under the layer mutex, and GamepadLayouts::Update already leaves the slots alone while the game holds its tables (`if (gameTables.Use()) return;`), which is why the full SavePreferences effect in sf4e__NetplayRuntime__Room.cxx calls SetLayouts unconditionally. Remedy: call Gamepads::SetLayouts unconditionally after a successful save, delete the branch and the paragraph that justifies it, and keep the menu-only rule where it actually lives (the pad Layout and RemoveLayout requests and the shell's CanEditLayout). Saved and applied layouts then cannot diverge whatever the shell sends.

### Note 2 (not blocking). The watcher save test depends on the writer not having started

TestWatcherSavesRoomSettings calls UseDirectoryForTest then StartPersistence, which returns early if a writer already exists. Nothing else in SpectatorRuntime starts one today, so it saves to the temp folder; a later test that starts persistence earlier in main() would silently send this test's save to the user's settings folder. Remedy: CHECK that no writer is running before StartPersistence (or stop persistence first), so the test fails rather than writes outside its folder.
